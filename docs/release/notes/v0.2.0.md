# Covalent v0.2.0 release candidate

## Status

`0.2.0` is the next release candidate, not a published release. There is no
`v0.2.0` tag, release asset, replacement container digest, cosign signature, or
attestation yet. No Atlas
or Unraid deployment has been performed. The pinned `v0.1.0` digest remains
historical-only and must not be installed for this workflow.

Personal-use native scope is an ad-hoc-signed Apple Silicon macOS app and a
debug-signed Android APK. Apple Developer ID/notarization is excluded. Android
production signing is deferred; neither is a blocker for this personal-use
release.

## What changes

- Long-lived node secrets, including identity, backup, recovery, TLS, and local
  API-token material, now use versioned authenticated key envelopes. Docker and
  Unraid require a separately mounted owner-only KEK; macOS uses the
  data-protection Keychain; Android uses Android Keystore. A missing, wrong, or
  unavailable protector fails closed.
- A new server without an owner is claimed only through `covalent claim` over
  verified HTTPS. The CLI verifies the delivered CA and exact hostname before
  writing its owner-only token output. Native apps and the web console accept a
  claimed token only, never a setup code.
- Existing deployments which already have a local API token migrate to the
  durable **claimed** lifecycle. They do not become claimable again and do not
  print a replacement setup code after upgrade.
- Terminal backup/archive results are retained until an explicit acknowledgement.
  Current clients persist the request/result before acknowledging; retries use
  the same job identity. Retained receipts provide crash recovery and bounded
  backpressure instead of silently discarding a completed result.
- Provider leases and capacity decisions are durable and bounded. The default
  content-defined chunk average is now 512 KiB; existing manifests retain their
  recorded boundaries and remain readable, but a new snapshot can have less
  cross-version deduplication.
- The exact 1 GiB provider-only source-loss gate passed twice consecutively on
  Apple Silicon at 26.127 MiB/s and 25.860 MiB/s for complete backup. Both runs
  restored the exact source digest, stayed below the 192 MiB RSS-growth limit,
  and stayed inside the enforced disk-amplification limit. These are validation
  measurements, not a throughput promise for every disk or network.

## Upgrade requirements

1. Stop the old node and make a verified, separate backup of `/config` and
   `/data` before changing it.
2. For Docker or Unraid, provision one version-1 KEK outside appdata and every
   selected backup source, retain an offline escrow, and mount only that file at
   `/run/secrets/covalent-kek`. Never place the KEK in `/config`, `/data`, a
   source share, or a Covalent backup.
3. Preserve `/config`, `/data`, and the same KEK together as the node's recovery
   set. Start the v0.2.0 image only after its published immutable digest has been
   independently verified and substituted atomically into the template.
4. Upgrade every active node/provider and every web, CLI, Android, and macOS
   client as one maintenance boundary before starting new work. v0.1.0 peers
   speak QUIC transport v2 while v0.2.0 peers speak transport v3, so mixed
   versions cannot exchange provider traffic. The new ALPN and signature domain
   fail closed rather than accepting old framing. Let each client retry and
   acknowledge any retained terminal result. Do not remove receipt state to
   make room for another job.
5. A server with an existing token stays owned. For a genuinely new server, use
   the verified CLI claim flow and enroll its generated CA; do not enter setup
   codes in the web or native clients.

The migration code is tested for legacy state readers, but this is a `0.x`
breaking release. Keep an independently restorable copy until a real upgrade
and restore drill has completed on the target host.

## Supported release scope

Tier 1 scope is Android, Apple Silicon macOS, Docker, and Unraid. macOS is
arm64-only; there is no Intel or universal build. iOS is informational source
only and is not a supported or published platform. Atlas and other Tailnet
hosts use explicit MagicDNS reachability and confirmed pairing; the stock
container does not run Tailscale or access its LocalAPI socket.

replacement digest exists.
